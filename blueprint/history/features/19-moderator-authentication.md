## Feature 19: Moderator authentication

**Branch:** `feature/moderator-authentication`
**Status:** verified

## Goal

Let a Moderator reach the existing `/m/<slug>` URL (its QR code was already
generated by Feature 7), enter the event's shared password, and receive an
event-scoped session that a later feature (20) uses to gate the actual
moderation queue. Moderators have no account (per the overview's user
table: "Per-event password... several moderators can share it"), so this
feature's whole job is turning one shared secret into a secure,
rate-limited, expiring session - nothing about individual moderator
identity.

## In scope

- **Migration adding three columns to `event_settings`:**
  `moderator_password_hash text` (nullable - null means no password has
  ever been set), `moderator_failed_attempts integer not null default 0`,
  `moderator_locked_until timestamptz` (nullable). The existing
  `events.moderator_access_enabled boolean` (Feature 1) and the existing
  `moderator_sessions` table (`event_id`, `session_token` unique,
  `expires_at`, `revoked_at` - also Feature 1) are reused as-is; neither
  needs a schema change.
- **`server/utils/verify-event-access.ts` (new shared helper).** Every
  existing admin server route (`verify-administrator.ts`) only allows
  Administrators; this is the first admin-facing route an Event Manager
  must also be able to call (setting the password for their own assigned
  event), matching `event_settings`'s own RLS predicate
  (`is_administrator OR is_event_manager_for`). Re-derives the caller from
  the bearer token via `supabase.auth.getUser(token)`, then: Administrator
  (non-deleted) is always authorized; an Event Manager (non-deleted) is
  authorized when `em_scope = 'global'` or a non-deleted
  `event_manager_assignments` row links them to the target event id.
  Returns the profile id or `null`, mirroring `verify-administrator.ts`'s
  shape.
- **Settings tab (`/admin/events/[id].vue`):** a "Moderator access enabled"
  switch, fetched/saved exactly like `submissionsOpen`/`votingOpen` (same
  `events` update inside the existing `saveSettings()`). Separately, a
  "Moderator password" password-style `UInput` with its own "Set password"
  button and its own save function - left blank on load and after every
  save (write-only, never fetched or displayed), since it goes through a
  different, hashing server route rather than the plain client-side
  `event_settings` update every other Settings field uses. Leaving it
  blank and clicking outside it does nothing; a value must be entered and
  the button clicked to change the password.
- **`server/api/admin/events/[id]/moderator-password.post.ts` (new).**
  Body `{ password }`. Requires `verify-event-access`; `401` when it
  fails. Rejects (`400`) a password under 8 characters. On success, hashes
  with Node's built-in `crypto.scryptSync` (64-byte derived key, a fresh
  16-byte `crypto.randomBytes` salt per password, stored as a single
  self-describing string `scrypt:<saltHex>:<hashHex>` - no new
  dependency, matching this project's existing zero-extra-crypto-lib
  footprint) and writes it to `event_settings.moderator_password_hash`,
  **also resetting `moderator_failed_attempts` to 0 and
  `moderator_locked_until` to null** - a fresh password starts with a
  clean attempt counter.
- **`server/api/events/[slug]/moderator-login.post.ts` (new, public).**
  Body `{ password }`. Resolves the event by slug the same way
  `questions.get.ts` does (`status = 'live'`, not soft-deleted); any
  resolution failure, plus `moderator_access_enabled = false`, all return
  the same generic `EVENT_NOT_FOUND_ERROR` used everywhere else in this
  app - no way to distinguish "wrong slug" from "moderator access is
  turned off" from an anonymous caller. Then, in order: if
  `moderator_locked_until` is still in the future, return `429` "Too many
  attempts. Please try again later." without checking the password at
  all; if it is in the past (or null) but attempts are non-zero from an
  expired lock, proceed normally (the next check clears it). If
  `moderator_password_hash` is null (no password ever set) or the
  submitted password doesn't verify against it (`timingSafeEqual` on the
  derived key, never a plain `===` on hash strings), increment
  `moderator_failed_attempts`; at 5 failed attempts, set
  `moderator_locked_until = now() + 15 minutes` and reset
  `moderator_failed_attempts` to 0, returning the same lockout message as
  above; below 5, return `400` "Incorrect password." Neither error
  reveals which specific condition triggered it or how many attempts
  remain. On a correct match, reset `moderator_failed_attempts` to 0 and
  `moderator_locked_until` to null, insert a `moderator_sessions` row
  (`session_token`: `crypto.randomBytes(32).toString('hex')`,
  `expires_at`: now + 12 hours - long enough to cover one event day),
  and return `{ sessionToken, expiresAt }`.
- **`server/api/events/[slug]/moderator-session.get.ts` (new, public).**
  Query `?token=`. Re-resolves the event by slug exactly as the login
  route does (`status = 'live'` and `moderator_access_enabled`, both
  re-checked on every call, matching `join.post.ts`'s precedent of never
  trusting a previously-valid state); returns `{ valid: false }` on any
  resolution failure instead of an error (this is a routine "is my stored
  session still good" check, not a user-facing action). Otherwise looks up
  the `moderator_sessions` row by `session_token`, confirms it belongs to
  *this* resolved event id, is not soft-deleted, `revoked_at is null`, and
  `expires_at` is in the future; returns `{ valid: true }` or `{ valid:
  false }` accordingly. Never returns the token or any other session
  field.
- **`app/utils/moderator-session.ts` (new)**, mirroring
  `device-identity.ts`'s shape: `getStoredModeratorSession(eventId):
  { sessionToken: string, expiresAt: string } | null` and
  `setStoredModeratorSession(eventId, session)` /
  `clearStoredModeratorSession(eventId)`, all `localStorage`-backed with
  the same in-memory-fallback `try/catch` pattern, keyed by the event's
  immutable `id` (never `slug`), matching Feature 12's rationale exactly.
- **`app/pages/m/[slug].vue` (new, no `admin` middleware - fully
  public).** Loads `{ id, name }` via the existing
  `GET /api/events/[slug]` context endpoint (already public, already
  resolves live-event-by-slug - reused rather than duplicated for this
  page's minimal needs). On a not-found result, renders "Event not
  found." and stops. Otherwise: if a locally stored session exists for
  this event id, calls the new session-verification endpoint; a `valid:
  true` result skips straight to a plain placeholder ("You're in. The
  moderator queue is coming soon."); anything else (no stored session, or
  `valid: false`) clears any stale stored session and shows a password
  form (one field, one "Enter" button). Submitting posts to the login
  route; on success, stores the returned session locally and shows the
  same placeholder; on failure, shows the returned message inline and
  leaves the form in place.

## Out of scope

- **The actual moderator queue, or any moderation action** (approve,
  reject, hide, archive, mark answered, change topic, open/close
  submissions or voting) - Feature 20 owns all of that; this feature's
  post-login placeholder is the same kind of expected forward-reference
  gap Feature 12 established for `/e/<slug>` before Feature 13 existed.
- **Explicit logout or session revocation.** `moderator_sessions.revoked_at`
  already exists in the schema (Feature 1) but nothing sets it yet, in
  this feature or any prior one; adding a revoke action is new,
  unrequested scope. A session simply expires after 12 hours.
- **Any per-moderator identity, display name, or "who is moderating"
  tracking** - the overview is explicit that several moderators share one
  event-scoped session; there is no moderator account or profile to
  attach.
- **IP-based, device-based, or global rate limiting** - Feature 30 (Abuse
  protection modes) owns that; this feature's rate limiting is scoped
  only to the one thing its own build-plan line asks for: attempts against
  one event's password, tracked on that event's own settings row.
- **Surfacing "is a moderator password currently set" anywhere in the
  admin UI**, or letting the admin view/reveal the current password - the
  field is write-only by design; the hash is never selected by any
  client-facing query.
- **Forced password rotation, complexity rules beyond the 8-character
  minimum, or a "confirm password" second field** - not asked for, and
  this project's other password flow (Event Manager account creation)
  has none of these either.
- **Applying `accentColor`/`backgroundColor`/`themeMode` or any real visual
  design to `/m/<slug>`** - same precedent as `/e/<slug>` pre-Feature-13:
  plain, unstyled-beyond-Nuxt-UI-defaults, since no moderator-surface
  visual design exists anywhere in this project yet.
- **Changing `submissions_open`/`voting_open` gating, or anything about the
  attendee-facing surfaces** - this feature only touches the moderator
  entry path.

## Data / contracts

- **The password is write-only end to end.** No client query, admin page
  field, or API response ever returns `moderator_password_hash` or the
  plaintext password; the admin's "Set password" field is always blank on
  load and after saving.
- **Rate limiting is per-event, not per-device or per-IP** - counters and
  lockout live on that event's own `event_settings` row, matching this
  feature's specific build-plan scope (broader abuse protection is
  Feature 30's job).
- **Every reason a login attempt can fail before the password check
  (unknown slug, non-live event, moderator access disabled) collapses
  into the same generic "Event not found."**, matching every other public
  endpoint's anti-enumeration convention in this app; a wrong password and
  a lockout are the only two distinguishable failure messages, and neither
  reveals which specific rule triggered it or how many attempts remain.
- **Hashing uses Node's built-in `crypto` module only** (`scryptSync` +
  `timingSafeEqual`, self-salted per password) - no new dependency, and
  the same "no unnecessary deps" pattern this project has followed since
  Feature 1 (no `zod`, despite the stack notes suggesting it, is already
  the established precedent).
- **A session is scoped to `(event_id, session_token)` together**, not the
  token alone, and its validity (event still live, moderator access still
  enabled, not expired, not revoked) is re-checked on every verification
  call rather than cached from the login response - the same
  never-trust-a-cached-state discipline `join.post.ts` already
  established for repeat attendee joins.
- **Setting a new password resets the attempt counters.** This is a
  deliberate choice: it lets an admin who just changed the password
  immediately test it without inheriting an old lockout, at the minor,
  accepted cost of also clearing out an attacker's in-progress attempt
  count on the rare, admin-initiated event of a password change.
- **The device-identity precedent (key by immutable event `id`, never
  `slug`; `try/catch` around every `localStorage` call with an in-memory
  fallback) applies identically to the new moderator-session storage
  utility.**

## Notes for the AI

- Do not build the moderator queue or any moderation action here - only
  the password gate and the placeholder it leads to.
- Do not add a logout/revoke action - `revoked_at` stays unused, as it has
  since Feature 1.
- Do not add per-moderator identity, accounts, or display names.
- Do not add IP-based or device-based rate limiting - only the per-event
  counters on `event_settings`.
- Do not let the admin page, or any server response, ever return
  `moderator_password_hash` or the plaintext password.
- Do not compare password hashes with `===` - use `crypto.timingSafeEqual`
  on the derived keys.
- Do not key the client-side moderator session by `slug` - use the
  event's immutable `id`, exactly like `device-identity.ts`.
- Do not skip re-checking `status = 'live'` and `moderator_access_enabled`
  on the session-verification endpoint - it must not trust that a
  previously valid session is still valid without checking.
